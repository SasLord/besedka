# Беседка — план корпоративного чата (Go-сервер + Tauri-клиент)

Название сервиса: **Беседка** (Besedka). Идентификатор для кода, репозитория, crate и службы: `besedka` (наличие имени в crates.io, на GitHub и в DNS проверить перед созданием репозитория).

Названия в интерфейсе:

| Элемент | Название |
|---|---|
| Сервис, приложение, служба Windows | **Беседка** |
| Общий чат для всех (комната `general`) | **Болталка** |
| Комнаты, созданные пользователями | **Переговорки** |
| Объявления и обязательные голосования (раздел Специалиста, очередь показа) | **Оперативка** |
| Канал «только для чтения» | **Новости** |

Статус: план v4 (открытых вопросов по требованиям нет, можно начинать этап 0). Код не писался.

Изменения v4: «Новости» — реакции без ответов; итоги голосований: в комнатах всем, в массовых по выбору автора; параметры «Позже» по умолчанию 30 минут / 5 откладываний (задаёт автор); анонимность выбирается при запуске любого голосования; прореживание бэкапов включено по умолчанию.

Изменения v3: каналы «только для чтения» (канал «Новости» создаётся сразу); голосования (в комнатах — любой, массовые — Специалист/Администратор, поверх окон); бэкапы: папка и срок хранения настраиваются (по умолчанию `backups` рядом с сервером, 1 год); Администратор видит все диалоги, удалённые — на розовом фоне с возможностью скрыть; группы можно синхронизировать из AD (задел на будущее); лимит комнат на пользователя — настройка, по умолчанию без ограничений.

Изменения v2: имя хоста сначала `web.cmy.local`, затем переезд на `chat.cmy.local`; файл до 1 ГБ и настраиваемая квота; группы пользователей (CRUD, рассылка по группам); история хранится бессрочно; резервное копирование по расписанию и вручную; тосты поверх окон; веб-версия и мобильные push перенесены на конец.

## 1. Исходные требования и принятые решения

| Вопрос | Решение |
|---|---|
| Масштаб | до 300 пользователей, онлайн 150–200, объём сообщений небольшой |
| Сервер | Go, Windows (в домене), также сборки под Linux/macOS |
| БД | SQLite (`modernc.org/sqlite`, без CGO), режим WAL |
| Клиент | Tauri 2 (Rust-оболочка + веб-UI на TypeScript), сборки Windows/Linux/macOS |
| Транспорт | только HTTPS и WSS, отдельный порт (по умолчанию **9443**, настраивается; занятые: 80, 443, 8443) |
| Безопасность | обычное разграничение доступа по ролям, шифрование «на диске» не нужно |
| Имя сервера | сначала `web.cmy.local:9443`, позже `chat.cmy.local` (см. раздел 4) |
| Файлы | максимум 1 ГБ на файл (настраивается); квота хранилища: число в ГБ или «максимум — сколько есть места на диске» (настраивается) |
| Группы | CRUD групп вручную (в AD групп нет), формируются по отделам; используются для адресации объявлений и массового приглашения в комнаты |
| Хранение сообщений | бессрочно; резервное копирование по расписанию и вручную; папка и срок хранения копий настраиваются (по умолчанию `backups` в папке запуска сервера, хранить 1 год) |
| Каналы | тип комнаты «канал» с режимом «только чтение»: писать могут только Специалист и Администратор; канал «Новости» создаётся автоматически, все пользователи — подписчики |
| Голосования | в комнатах — любой участник; массовые (поверх окон, обязательные, с кнопкой «Позже») — Специалист и Администратор; отдельный раздел управления и отчётов |
| Лимиты | число комнат на пользователя — настройка (по умолчанию без ограничений; при необходимости можно задать, например, 100) |
| Уведомления | красивые тосты поверх окон в углу экрана (этап 2); push для мобильных и веб-версия — в самом конце |
| Будущее | сервис внутри платформы на Rust: интеграция через стабильный контракт API, а не через общий язык |

Примечание: в ТЗ был порт «433», считаю опечаткой для 443. Порт сервера вынесен в `.env`.

## 2. Роли

- **Администратор** — всё, что у Специалиста, плюс: управление пользователями (в т. ч. не доменными) и группами, объединение учёток, **просмотр всех комнат и личных диалогов** (удалённые сообщения показываются на розовом фоне; их показ можно скрыть переключателем), статистика, мониторинг и настройка хранилища файлов, резервное копирование.
- **Специалист** — рассылка объявлений (всем, по группам или выбранным пользователям), массовые голосования, публикация в каналах «только для чтения» (например, «Новости»), статистика и отчёты по объявлениям и голосованиям. Группы он видит и использует, редактирует только Администратор.
- **Сотрудник** — личные диалоги, комнаты (создание, приглашение, исключение участников), чтение каналов, файлы, реакции, ответы, запуск голосований внутри своих комнат.

Права комнаты (владелец/участник) независимы от глобальной роли.

## 3. Архитектура

```
[Tauri-клиент] --WSS/HTTPS--> [Go-сервер :9443] --> SQLite (WAL)
   Rust-ядро: SSPI,                REST + WebSocket          + каталог файлов на диске
   трей, автозапуск,               auth, чат, объявления,    (по хэшу, с квотами)
   окно объявлений, тосты          файлы, админка, бэкапы
   Веб-UI (TS): чат, редактор
```

Структура сервера (Go): `cmd/server`, `internal/{auth,users,groups,chat,announce,files,admin,stats,backup,db,ws,config}`.
Структура клиента: `src-tauri` (Rust) + `ui` (TypeScript).

**UI-фреймворк: Svelte 5 (решено).** Используем SvelteKit в режиме SPA (`adapter-static`, `ssr = false`): он даёт готовые layout-ы и файловую маршрутизацию, при этом результат — статические файлы, которые подходят и для Tauri, и для отдачи сервером в веб-версии. Принципы:
- Layout-ы и шаблоны везде, где возможно: корневой `+layout.svelte` (тема, подключение WS, глобальные сервисы), layout приложения с боковым списком чатов, отдельный layout админки/раздела Специалиста с меню и проверкой роли, отдельные минимальные layout-ы для окна объявления/голосования и для окна тоста (разные окна Tauri — разные точки входа).
- Общая библиотека компонентов (кнопка, модальное окно, выпадающий список, чип, аватар, пустое состояние, таблица, форма) и дизайн-токены в CSS-переменных (тёмная/светлая темы); один и тот же компонент рендерит форматированный текст сообщений, объявлений и голосований.
- Обёртка над Tauri API (адаптер), чтобы тот же UI работал в браузере без Tauri.
- Состояние — Svelte runes/stores; типы запросов генерируются из OpenAPI; редактор — TipTap внутри Svelte-компонента.

Принципы:
- Единый версионированный контракт: OpenAPI для REST и описанный JSON-протокол для WS (`/api/v1`, поле `v` в WS-кадрах). Это основа будущей интеграции с Rust-платформой.
- Сквозной порядковый номер сообщений в каждой комнате (`seq`): офлайн-синхронизация сводится к запросу «всё после N».
- Сервер единственный источник правды, клиент хранит только кэш.
- Веб-интерфейс чата пишется как самостоятельное TS-приложение без привязки к Tauri API (обращения к ОС — через тонкий слой-адаптер), чтобы позже тот же UI отдавать как веб-версию.

## 4. Авторизация

### Доменный вход (Windows в домене)
Предпочтительный вариант: **клиент сам получает Kerberos-токен через SSPI** (Rust, крейт `windows`, `InitializeSecurityContext` с пакетом Negotiate, SPN `HTTP/<имя сервера>`) и отправляет его на `POST /api/v1/auth/negotiate`. Сервер валидирует токен через `gokrb5` и keytab, находит или создаёт пользователя по `objectSid`, выдаёт токен сессии.

Плюсы: не зависим от поведения WebView и политик браузера, полный контроль над потоком.
Запасной вариант: Negotiate на уровне WebView2 (флаг `--auth-server-allowlist`, политика через GPO). Выбор по итогам спайка.

### Переезд с `web.cmy.local` на `chat.cmy.local`
SPN не содержит порта, поэтому на старте можно переиспользовать SPN `HTTP/web.cmy.local` и существующий keytab (сервер на том же хосте). Проверить на спайке. Чтобы переезд прошёл без переписывания кода:
- имя сервера и SPN — параметры конфигурации (`SERVER_HOST`, `SPN_NAMES`), нигде не зашиты в код;
- сервер умеет принимать несколько SPN одновременно (keytab с обоими именами), на период перехода работают оба имени;
- адрес сервера в клиенте берётся из GPO/реестра: смена адреса = смена одного значения политики, переустановка клиента не нужна;
- TLS-сертификат сразу выпускается с двумя SAN (`web.cmy.local`, `chat.cmy.local`);
- при переезде: DNS-запись (A или CNAME) для `chat.cmy.local`, `setspn` для `HTTP/chat.cmy.local` на ту же служебную учётку, пересоздание keytab с обоими SPN, обновление политики с адресом.
- Сессии привязаны к пользователю, а не к имени хоста, поэтому история и учётки сохраняются.

### Вход вне домена, а также macOS/Linux
Логин и пароль (хэш Argon2id), выдача токена сессии, ограничение числа попыток, блокировка по IP.

### Объединение учёток
Таблица `identities`: у одного пользователя может быть и AD-идентичность (`sid`), и локальный пароль. Администратор привязывает одно к другому. Человек в домене входит автоматически, вне домена — по логину/паролю, а попадает в тот же профиль.

### Сессии
Короткоживущий access-токен + refresh, хранение хэша refresh в БД, отзыв сессий администратором. WS-подключение аутентифицируется токеном при апгрейде.

## 5. Модель данных (SQLite)

Основные таблицы (черновик):

- `users` (id, display_name, role, status, avatar_file_id, created_at, disabled_at)
- `identities` (id, user_id, kind `ad|local`, ad_sid, ad_login, local_login, password_hash)
- `groups` (id, name, description, sort_order, created_at, source `manual|ad`, ad_key) — отделы и произвольные группы; `source=ad` — группа синхронизируется из AD
- `group_members` (group_id, user_id, added_at, source `manual|ad`); пользователь может состоять в нескольких группах
- `settings` содержит также `max_rooms_per_user` (0 = без ограничений), параметры AD-синхронизации групп (вкл/выкл, источник, период)
- `sessions` (id, user_id, refresh_hash, device, created_at, last_seen, revoked_at)
- `rooms` (id, kind `direct|room|channel|general`, title, icon, owner_id, created_at, last_seq, post_policy `all|staff` (для канала `staff` = писать могут только Специалист и Администратор), system_key (например `news`))
- `room_members` (room_id, user_id, role `owner|member`, joined_at, left_at, muted, last_read_seq); для общих каналов («Новости») подписчики добавляются автоматически при создании пользователя
- `messages` (id, room_id, seq, author_id, body_json, body_text, reply_to_id, created_at, edited_at, deleted_at, deleted_by, erased_at); физически не удаляются
- `message_files` (message_id, file_id, position)
- `reactions` (message_id, user_id, emoji, created_at); лимит 3 на пользователя на сообщение, при превышении вытесняется самая старая
- `reaction_freq` (user_id, emoji, use_count) — частые реакции
- `files` (id, sha256, size, mime, original_name, uploader_id, created_at, storage_path, preview_path, refcount)
- `announcements` (id, author_id, title, body_json, buttons_json, created_at, expires_at, audience_kind `all|groups|users`)
- `announcement_audience` (announcement_id, kind `group|user`, target_id) — исходные адресаты
- `announcement_recipients` (announcement_id, user_id, delivered_at, shown_at, clicked_button, clicked_at) — список раскрывается при отправке (состав группы фиксируется на момент рассылки)
- `polls` (id, scope `room|broadcast`, room_id, author_id, question_json, kind `single|multi`, anonymous (выбирается при запуске), results_visibility `all|author` (по умолчанию: комната — `all`, массовое — выбирает автор), allow_change, created_at, closes_at, closed_at, mandatory, postpone_interval_min (по умолчанию 30), postpone_max (по умолчанию 5), audience_kind `all|groups|users`)
- `poll_options` (id, poll_id, position, text)
- `poll_audience` (poll_id, kind `group|user`, target_id) — исходные адресаты массового голосования
- `poll_recipients` (poll_id, user_id, delivered_at, shown_at, postponed_count, last_postponed_at, voted_at) — для массовых голосований
- `poll_votes` (poll_id, user_id, option_id, voted_at); при анонимном голосовании связь с пользователем хранится только в `poll_recipients.voted_at` (факт участия), а выбор — без user_id
- `backups` (id, kind `scheduled|manual`, started_at, finished_at, status, path, size, db_only, error)
- `audit_log` (id, actor_id, action, target, details_json, created_at) — действия администраторов
- `settings` (key, value) — максимальный размер файла, квота, расписание бэкапов, лимиты

Индексы: `messages(room_id, seq)`, `room_members(user_id)`, `group_members(user_id)`, `announcement_recipients(user_id, clicked_at)`.

## 6. Чат

- **Редактор:** TipTap (ProseMirror). Формат хранения — JSON-документ (не markdown), плюс `body_text` для поиска и превью. Поддержка: заголовки, жирный, курсив, подчёркнутый, зачёркнутый, маркированный и нумерованный списки, ссылки, цитата, цвет текста.
- **Санитизация:** белый список узлов/марок и допустимых значений цвета на сервере; тот же набор правил для объявлений.
- **Ответы** (reply) с цитатой оригинала и переходом к нему.
- **Реакции** (до 3 на сообщение от одного пользователя), панель частых реакций.
- **Информация о сообщении:** кто прочитал (по `last_read_seq`) и кто какую реакцию поставил.
- **Редактирование и удаление:** мягкое удаление; администратор видит удалённые.
- **Просмотр администратором:** Администратор видит все комнаты и личные диалоги (раздел «Все чаты» в админке, режим только чтения). Удалённые сообщения отображаются полным текстом на розовом фоне; переключатель «Показывать удалённые» позволяет скрыть их. Каждое открытие чужого диалога фиксируется в журнале аудита (прозрачность и защита самого администратора); пользователей об этом стоит предупредить в регламенте.
- **Комнаты:** создание, приглашение и исключение участников; приглашение целой группы одним действием (участники копируются в комнату в момент приглашения). Лимит комнат на пользователя — настройка `max_rooms_per_user` (по умолчанию 0 = без ограничений).
- **Каналы «только для чтения»:** тип комнаты `channel` с политикой `staff`: писать, редактировать и удалять свои публикации могут только Специалист и Администратор, остальные читают, ставят реакции и отвечают в обсуждении только если оно разрешено настройкой канала (по умолчанию — реакции без ответов). Канал **«Новости»** создаётся автоматически при первой установке (`system_key=news`), все пользователи подписаны и не могут отписаться; уведомления можно заглушить. Специалист/Администратор могут создавать и другие каналы.
- **Голосования в комнатах:** любой участник комнаты может создать голосование (вопрос, варианты, один/несколько вариантов, анонимное или открытое, возможность менять голос, срок). Опрос отображается карточкой в ленте с живыми результатами по WS; создатель и Администратор могут закрыть голосование досрочно. Подробности — раздел 8.1.
- **Непрочитанные, отключение уведомлений по комнатам, список онлайн** (в стиле Telegram).
- **История хранится бессрочно.** Автоудаления нет; рост БД контролируется статистикой и бэкапами. Подгрузка истории постраничная по `seq`.
- **Поиск** по `body_text` (FTS5) — этап 2/6.
- **Эмодзи:** собственный набор, одинаковый на всех ОС. Кандидаты: Fluent Emoji (MIT) или Twemoji (CC-BY 4.0, нужно указание авторства). Выбрать на этапе 0 и учесть лицензию.
- **Оформление:** тёмная и светлая темы, пузыри сообщений, список чатов слева, как в Telegram.

## 7. Файлы

- **Максимальный размер файла: 1 ГБ** (по умолчанию, значение меняется в настройках администратором).
- **Квота хранилища** задаётся в настройках одним из двух способов: числом в ГБ или режимом «максимум» (ограничение — свободное место на диске, с резервом, например 5 ГБ, чтобы не заполнить системный диск). Режим и число меняются без перезапуска.
- Загрузка чанками с возобновлением (обязательно из-за 1 ГБ), потоковая запись на диск без загрузки файла в память, потоковая отдача с поддержкой Range (просмотр видео, докачка).
- Перед стартом загрузки сервер проверяет лимит файла, квоту и свободное место; ошибка понятна пользователю («хранилище заполнено»).
- Хранение на диске по SHA-256 (дедупликация), метаданные в SQLite. Каталог файлов настраивается (можно вынести на отдельный диск).
- Превью: изображения (миниатюры на сервере), PDF и видео — средствами клиента/WebView; прочее — иконка и скачивание.
- Скачивание только по авторизованному запросу и с проверкой членства в комнате.
- Мониторинг для администратора: занято/квота/свободно на диске, предупреждения при 80% и 90%, список самых больших файлов, возможность удаления файла администратором (с аудитом), опционально — политика очистки по возрасту (по умолчанию выключена).
- Вопрос безопасности: антивирусная проверка — вне MVP, оставить точку расширения.

## 8. Объявления

- Создаёт Специалист или Администратор в отдельном разделе: заголовок, текст с тем же форматированием, набор кнопок (1..N, у каждой — подпись и идентификатор), адресаты, срок действия.
- **Адресаты:** все пользователи, одна или несколько **групп**, выбранные пользователи или их сочетание. Дубликаты (человек в нескольких группах) схлопываются. Состав получателей фиксируется в `announcement_recipients` в момент отправки.
- Доставка: push по WS; если клиент офлайн — при подключении. Статусы: `delivered` → `shown` → `clicked(button)` с временем.
- Окно клиента: безрамочное, поверх всех окон, на весь экран (каждый монитор), затемнение фона; по возможности размытие (acrylic на Windows, vibrancy на macOS; на Linux — только затемнение). Закрытие только кнопкой объявления, Alt+F4 и Esc перехватываются.
- Ограничения, о которых нужно знать: размытие содержимого других приложений кроссплатформенно не гарантируется; на уровне ОС окно принудительно не закрыть нельзя (диспетчер задач, Ctrl+Alt+Del), для штатного сценария этого достаточно.
- Статистика для Специалиста: получено / показано / ждёт реакции, разбивка по кнопкам и по группам, список пользователей и времени, экспорт в CSV.
- Очередность нескольких объявлений: показываются по одному, по порядку.

## 8.1. Голосования

### В комнатах (любой участник)
- Создание из меню комнаты: вопрос (с форматированием), 2–N вариантов, режим (один / несколько вариантов), открытое или анонимное, можно ли менять голос, срок окончания (необязательный).
- Результаты в ленте обновляются в реальном времени (WS), для открытых голосований видно, кто за что проголосовал; закрыть досрочно может автор или Администратор. После закрытия результат фиксируется в сообщении.
- Голосовать могут только участники комнаты (в личных диалогах — оба собеседника).

### Массовые (Специалист и Администратор)
- Адресаты — как у объявлений: все, группы, выбранные пользователи. Состав фиксируется в момент запуска.
- Показ клиенту: полноэкранное окно поверх всех окон с затемнением (и размытием по возможности), по центру карточка с вопросом и вариантами. Голосование **обязательное**, но у окна есть кнопка **«Позже»**: окно скрывается, голосование остаётся в разделе **«Голосования»** клиента (список активных голосований, ожидающих ответа; значок-счётчик), откуда его можно открыть в любой момент. Политика напоминаний настраивается (повторный показ через N минут/при следующем входе, максимум N откладываний, после которого «Позже» скрывается — по решению автора).
- Если у пользователя есть несколько ожидающих — показываются по очереди; объявления и голосования имеют общую очередь показа (объявление приоритетнее).
- Статусы адресата: доставлено → показано → отложено (число раз) → проголосовал. Для анонимных голосований хранится только факт участия, но не выбор.

### Раздел «Голосования» (Специалист/Администратор)
- Список голосований (черновики, активные, завершённые, фильтр по автору, статусу, дате).
- Создание и редактирование (до запуска), клонирование, запуск немедленный или по расписанию, досрочное закрытие, продление срока.
- Просмотр: прогресс (проголосовало / всего), диаграммы по вариантам, список проголосовавших и не проголосовавших (для открытых голосований), разбивка по группам, число откладываний.
- Отчёты: экспорт в CSV, итоговая сводка, напоминание не проголосовавшим (повторная рассылка).
- В клиенте у обычного сотрудника раздел «Мои голосования»: ожидающие ответа, пройденные, результаты (если автор их открыл).

## 9. Клиент (Tauri)

- Автозапуск, иконка в трее, сворачивание в трей.
- **Тосты (всплывающие уведомления о новых сообщениях):** собственное окно Tauri — безрамочное, прозрачное, всегда поверх остальных окон, не забирает фокус, появляется в углу рабочей области экрана (угол настраивается, учитывается панель задач и несколько мониторов). Содержимое: аватар, имя, комната, начало сообщения (с эмодзи нашего набора), анимация появления/скрытия, стопка до 3–4 тостов, автоскрытие по таймеру (пауза при наведении), клик открывает нужный чат на нужном сообщении, кнопка закрытия. Не показываются, если окно чата активно в этой комнате или комната заглушена; режим «не беспокоить»; уважаем состояние ОС (полноэкранные приложения/презентации). Дополнительно — резервный вариант на нативных уведомлениях ОС, если собственное окно недоступно (например, особенности Wayland на Linux).
- Rust-слой: SSPI-токен, хранение refresh-токена в системном хранилище секретов (Credential Manager / Keychain / Secret Service), окно объявлений, окно тостов, автообновление.
- Один экземпляр на пользователя (single-instance).
- Адрес сервера: из реестра (Windows, GPO), из конфиг-файла (Linux/macOS), либо диалог первого запуска.
- Проверка сертификата: доверие корпоративному корневому CA, который уже раздаётся по GPO; опция добавить свой CA в клиент для macOS/Linux.

## 10. Администрирование и статистика

- **Пользователи:** список, создание локальных, редактирование, отключение, смена роли, сброс пароля, объединение с AD-учёткой, принудительный выход (отзыв сессий).
- **Группы (CRUD):** создание, переименование, удаление групп; добавление и исключение участников (в том числе массовое); группы формируются по отделам; быстрый просмотр состава и количества участников; защита от удаления группы, на которую ссылаются незавершённые объявления (или предупреждение). Пользователей AD при первом входе можно распределять по группам вручную.
- **Автоматическое формирование из AD (задел на будущее):** сейчас в AD отдельных групп/отделов нет, поэтому по умолчанию функция выключена. Реализуем как необязательный модуль синхронизации: источник настраивается — группы безопасности AD (`member` / `memberOf`), атрибут `department` пользователя или конкретное OU; период синхронизации; сопоставление «значение AD → группа чата». Синхронизируемые группы помечаются `source=ad` (состав управляется AD, вручную добавленные участники не затираются, ручное исключение запоминается). Модуль включается переключателем в админке, когда в AD появится нужная структура; перезапуск и изменение схемы БД не потребуются.
- Удалённые сообщения: просмотр администратором (отдельный фильтр, с пометкой кто и когда удалил).
- **Хранилище:** настройка максимального размера файла и квоты (ГБ или «максимум по диску»), мониторинг заполнения, крупнейшие файлы.
- **Резервное копирование:** раздел в админке (см. раздел 11).
- Статистика: активность по дням, число сообщений, онлайн, топ комнат, объём файлов, заполнение хранилища, размер БД.
- Журнал аудита действий администраторов.

## 11. Резервное копирование

Выполняется в конце разработки (этап 6), но схему данных и настройки закладываем заранее.

- **Что копируется:** БД (согласованный снимок через `VACUUM INTO` или Online Backup API SQLite — без остановки сервера) и, опционально, каталог файлов (инкрементально: копируются только новые файлы, так как они неизменяемы и хранятся по хэшу).
- **Папка назначения:** задаётся в админке (локальный диск или сетевая папка, проверка доступности и прав записи при сохранении). **По умолчанию — папка `backups` в каталоге запуска сервера** (создаётся автоматически).
- **Срок хранения:** настраивается (число копий и/или срок в днях/месяцах), **по умолчанию 1 год**; ротация удаляет копии старше срока. Чтобы 1 год не раздул диск, **прореживание включено по умолчанию**: ежедневные копии хранятся 30 дней, затем одна в неделю до 12 недель, затем одна в месяц до истечения срока хранения (1 год). Схема и срок настраиваются, прореживание можно отключить.
- **По расписанию:** встроенный планировщик в сервере; расписание задаётся в админке (например, ежедневно в 02:00); параметры: включать ли файлы.
- **Вручную:** кнопка «Создать копию сейчас» в админке, отображение прогресса и результата, скачивание/копирование снимка БД.
- **Контроль:** история копий (таблица `backups`: когда, тип, размер, статус, ошибка), оповещение администратору при неудаче (уведомление в клиенте и запись в журнал), проверка свободного места перед запуском.
- **Восстановление:** документированная процедура (остановка службы, подмена БД и каталога файлов, запуск) и проверка восстановления на тестовой копии; проверка целостности копии (`PRAGMA integrity_check`).
- Копии не шифруются (по принятым требованиям), доступ к каталогу назначения ограничивается правами ОС.

## 12. Развёртывание

### Сервер
- Windows: один исполняемый файл + `.env`, запуск как служба Windows (`kardianos/service` или NSSM).
- Порт: `LISTEN_ADDR=:9443`, TLS-сертификат от корпоративного CA (SAN: `web.cmy.local` и `chat.cmy.local`).
- Каталоги данных (БД, файлы, бэкапы) настраиваются; рекомендуется держать их вне системного диска.
- Логи в файл с ротацией.

### Клиент
- Windows: MSI (WiX), подпись кода; GPO-публикация, ADMX-шаблон для адреса сервера и автозапуска.
- Автообновление с сервера (Tauri updater, подписанные пакеты).
- macOS: dmg (подпись/нотаризация по необходимости), Linux: AppImage/deb.

## 13. Безопасность

- Только TLS ≥ 1.2, WSS, HSTS для веб-части.
- Проверка прав на каждый запрос и WS-команду (членство в комнате, роль).
- Ограничение частоты запросов и размеров, защита от перебора паролей.
- Санитизация форматированного текста и имён файлов; `Content-Disposition`/`nosniff` при отдаче файлов.
- Аудит действий администратора; отзыв сессий.
- Секреты (keytab, ключи) вне репозитория, в `.env`/защищённых каталогах.
- Отключение HTTP/2 не требуется (в отличие от портала), так как SSPI-токен передаётся в теле/заголовке отдельного запроса, а не в рукопожатии WebView; подтвердить на спайке.

## 14. Этапы

**Этап 0. Спайки (2–4 дня)**
- Kerberos: SSPI-токен из Tauri → валидация в Go на реальном AD, SPN `HTTP/web.cmy.local`, проверка переиспользования keytab.
- Окно объявления: полноэкранное, затемнение, перехват закрытия на Windows (и проверка acrylic).
- Окно тоста: прозрачное, поверх окон, без фокуса, угол экрана, несколько мониторов.
- Каркас UI на SvelteKit (SPA, layout-ы) и выбор набора эмодзи.
- Проверка порта/сертификата на сервере (SAN с двумя именами).

**Этап 1. Каркас (1–2 недели)**
Сервер, конфиг, БД и миграции, авторизация (AD + локальная), роли, сессии, WS-слой, базовый клиент с входом и общим чатом.

**Этап 2. Полный чат**
Комнаты и диалоги, участники, **каналы «только для чтения» и канал «Новости»**, редактор с форматированием, ответы, реакции, статусы прочтения, эмодзи, файлы (чанки до 1 ГБ, превью, квоты), **голосования в комнатах**, непрочитанные, **тосты поверх окон**, трей, нативные уведомления как запасной вариант.

**Этап 3. Группы, объявления и массовые голосования**
CRUD групп (минимально необходимый для адресации), конструктор объявлений, адресаты (все / группы / пользователи), доставка, окно клиента, статистика Специалиста. Массовые голосования на общей инфраструктуре объявлений: окно с кнопкой «Позже», очередь показа, раздел «Голосования» (создание, просмотр, отчёты, экспорт) и «Мои голосования» в клиенте.

**Этап 4. Администрирование**
Пользователи, объединение учёток, управление группами (полный интерфейс, задел под синхронизацию с AD), раздел «Все чаты» (просмотр любых диалогов с розовой подсветкой удалённых и переключателем их скрытия, аудит просмотров), настройки хранилища (лимит файла, квота), лимит комнат, статистика, мониторинг хранилища, аудит.

**Этап 5. Дистрибуция**
MSI + GPO + ADMX, автообновление, сборки macOS/Linux, служба на сервере, подготовка переезда на `chat.cmy.local`.

**Этап 6. Резервное копирование и стабилизация**
Бэкапы по расписанию и вручную (раздел 11), восстановление и его проверка, нагрузочные тесты (200 WS-клиентов, загрузка файлов до 1 ГБ), безопасность, документация, стабилизация OpenAPI для интеграции с Rust-платформой.

**Этап 7. Веб-версия**
Отдача UI сервером в браузер, вход (доменный Negotiate через браузер и логин/пароль), ограничения (без окна объявлений поверх ОС — внутри вкладки, веб-уведомления).

**Этап 8. Мобильные клиенты и push (по решению позже)**
Решение по платформе (Tauri mobile / нативные / PWA), push-уведомления (FCM/APNs или собственный механизм для закрытой сети), адаптация объявлений.

## 15. Риски

| Риск | Что делаем |
|---|---|
| Kerberos в клиенте/сервере не заведётся «из коробки» | спайк на этапе 0; запасной вариант — Negotiate через WebView |
| Переезд на `chat.cmy.local` ломает вход | имя и SPN в конфигурации, несколько SPN в keytab, адрес сервера через GPO, сертификат с двумя SAN |
| Требование «нельзя закрыть объявление» упирается в ограничения ОС | заранее согласовать, что защита штатная, а не абсолютная |
| Размытие фона не везде | гарантированное затемнение, размытие как улучшение |
| Рост хранилища файлов при квоте «максимум по диску» | резерв свободного места, мониторинг и предупреждения, вынос каталога на отдельный диск |
| Файлы по 1 ГБ нагружают сервер и сеть | чанки, потоковая работа без буферизации в памяти, возобновление загрузки, нагрузочные тесты |
| Бессрочное хранение раздувает БД | индексы и постраничная загрузка, мониторинг размера БД, регулярные бэкапы, при необходимости архивация старых данных |
| Бэкап не восстанавливается | регулярная проверка восстановления и `integrity_check` |
| Хранение копий 1 год занимает много места (особенно с файлами) | инкрементальное копирование файлов, прореживание старых копий, проверка свободного места, предупреждение администратору |
| Администратор читает личные переписки | аудит каждого открытия, предупреждение пользователей в регламенте, возможность отключить функцию настройкой |
| Принудительное массовое голосование раздражает пользователей | кнопка «Позже», лимит откладываний и интервал напоминаний настраиваются автором |
| Анонимность голосования нарушается через журналы | для анонимных голосований выбор не связывается с пользователем в БД и логах |
| Синхронизация групп с AD затирает ручные правки | пометка `source`, ручные исключения запоминаются, функция выключена по умолчанию |
| Тосты ведут себя по-разному на ОС (Wayland, полноэкранные приложения) | запасной вариант на нативных уведомлениях, настройка угла и режима |
| WebView различается между ОС (WebView2/WKWebView/WebKitGTK) | тестирование на всех трёх, минимум нестандартного CSS/JS |
| Сложность редактора | готовая основа TipTap, структурный формат вместо markdown |
| Будущая интеграция с Rust-платформой | версионированный контракт, независимая БД, отсутствие связей с внутренностями |

## 16. Решённые вопросы (из v1)

1. Имя хоста: сначала `web.cmy.local` (порт 9443), затем `chat.cmy.local`.
2. Файл до 1 ГБ, квота настраиваемая (ГБ или «максимум по диску»).
3. Группы: CRUD, по отделам, ручное формирование, рассылка объявлений по группам.
4. Веб-версия: нужна, делаем в самом конце.
5. История бессрочно; бэкапы по расписанию и вручную — в конце.
6. Push на мобильные: в самую последнюю очередь; тосты поверх окон в углу экрана нужны сразу.

Решено дополнительно (v3): комнаты без лимита (настройка есть); каналы «только чтение» и «Новости»; папка и срок бэкапов настраиваются (по умолчанию `backups`, 1 год); Администратор видит все диалоги, удалённые — на розовом фоне, с возможностью скрыть; группы из AD — необязательный модуль на будущее; голосования в комнатах и массовые.

Решено дополнительно (v4):
- «Новости»: только чтение и реакции, ответов нет (настройка на уровне канала остаётся).
- Итоги голосований: в комнатах видны всем участникам, в массовых — по выбору автора.
- «Позже»: интервал напоминания 30 минут, максимум 5 откладываний; значения задаёт автор.
- Анонимность выбирается при запуске любого голосования (и в комнате, и массового).
- Прореживание бэкапов включено по умолчанию (30 дней ежедневно → 12 недель еженедельно → ежемесячно до 1 года).

## 17. Открытые вопросы

Открытых вопросов по требованиям нет. Остаются технические решения, которые принимаются на этапе 0 по результатам спайков: механизм Kerberos (SSPI в клиенте или Negotiate в WebView), набор эмодзи (Fluent или Twemoji), поведение окон объявления и тостов на разных ОС.
